# Stage-by-stage implementation

1. **Problem definition.** Estimate future daily personal expenditure and incoming receipts. Compare their seven-day totals to indicate Within budget or Exceeded, with Normal/Critical status. Success is measured on unseen chronological data, not a promised R² threshold.
2. **Data understanding.** Users upload PhonePe Date, Time, Transaction Details, Transaction ID, Transaction Type and Amount; UTR is optional and not used as a predictor. Daily totals use the date, not transaction time. Incoming and outgoing directions are separate. The dataset is personal transaction records, not questionnaire, convenience-sampling or Google Form responses.
3. **EDA.** Inspect counts, data types, daily distributions, outliers, correlations and category totals. The notebook plots these from local reviewed data. Explain observed patterns after running it; do not infer causal explanations from correlations.
4. **Hypothesis testing.** An optional exploratory question is whether mean spending differs between weekdays and weekends. Report the hypothesis, test assumptions and actual results if tested; this public template does not claim a completed statistical hypothesis test on an absent dataset.
5. **Preprocessing.** Reject invalid amounts, malformed dates, unknown directions and conflicting duplicate IDs. Store exact integer paise, normalize category identifiers, require manual categorization and confirm complete calendar days. Excluded transfers remain auditable but are not used for expense/credit totals. Valid large payments are not automatically discarded.
6. **Feature engineering.** Use one- and seven-day lags, shifted seven- and 28-day rolling means for both targets, sine/cosine weekday and day of month. Shifting ensures features contain only prior-day information. PCA is not needed for this small interpretable numeric feature set. Category IDs are not predictors, so one-hot encoding is not part of this model. Ridge standardizes numeric features within its pipeline; tree models do not need scaling.
7. **Data splitting.** Reserve the latest 20% of modelling dates for testing; use three expanding time folds on the earlier 80%. The first 28 days supply feature history. Report actual sizes from training metadata.
8. **Model building.** Train historical mean, Ridge, Extra Trees and Gradient Boosting separately for expenditure and credits. Fixed random seeds provide repeatable results. Credit estimation needs enough receipt events.
9. **Evaluation.** Report MAE and RMSE in rupees and R² on the holdout. Negative R² indicates poor predictive usefulness. The test predicts each day using known previous actual days; multi-day recursive rollout has additional uncertainty.
10. **Comparison and selection.** Select each target's model by lowest average chronological validation RMSE, then report held-out results for all candidates. Do not choose a winner using the test set. No classifier is necessary for an exact greater-than-budget rule.
11. **Tuning.** Tree depth and leaf size are constrained in the fixed candidate settings. This implementation does not claim a grid search or post-pruning study. Add further tuning within training folds only if needed; never tune to obtain a desired test score.
12. **Explainability.** Describe lag and calendar feature meanings. Category allocation uses observed recent debit shares; it is not feature importance or an explanation of the regression model's causal behavior.
13. **Deployment.** Save both regression models with their feature pipelines, metrics and data signature. The local website imports and reviews records, persists edits, retrains models and produces one-to-14-day forecasts (days 8–14 are explicitly marked exploratory) and category allocation. Stale models are blocked after data changes.
14. **Monitoring.** Compare saved predictions with actual completed-day totals when available. Review missing dates, excluded credits, category quality, changed spending habits and repeated prediction errors. Retrain after data changes; assess whether sufficient new data improves chronological validation. This template stores prediction history but does not claim an automated drift alarm.
15. **Final report.** Include actual row/date counts and measured results after using your own data. Explain privacy, single-person selection bias, limited coverage and uncertain future income. Do not report the synthetic example's metrics as your own financial performance.
16. **Presentation.** Demonstrate upload, persistent review, confirmed days, training, seven-day forecast, exact category totals, budget override, trash/restore and permanent-deletion confirmation. Explain the distinction between forecast labels and recorded spending.
